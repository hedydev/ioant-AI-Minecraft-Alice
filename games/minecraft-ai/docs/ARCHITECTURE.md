# Alice architecture

## Native Bedrock movement trust boundary (2026-10-19, staged)

Bedrock 1.26 autonomous Alice is separate from old Mint-local Paper/Mindcraft. Its pinned Mineflayer fork uses `bedrock_plugins/client_input.js` to send `player_auth_input` at about 20Hz; this is **not** the Java plugin's `position` / `position_look` stream. The server may send `correct_player_move_prediction` or an own `move_player`, which are read without mutation by `experiment/src/movement_evidence.cjs`. `bot.entity.position` is still predicted local physics and **cannot prove BDS movement**. Missing correction packets do not necessarily mean no movement. Final true-motion acceptance compares MCManager `querytarget` XYZ with the visible entity.

A direct-follow input fallback exists **only for A* noPath**: pure `safe_follow_step.cjs` requires an observed grounded position, flat player feet, valid known solid floor plus two-block headroom throughout a 0.6m wide corridor, nearby target, no known hostile near the step, and no current survival hazard. Its executor in `runtime.cjs` releases a failed A* goal, turns, sets only forward input for 400ms, stops and imposes a retry cooldown if progress is not verified. No teleport, block editing, unbounded movement or bypass of player STOP/safety arbitration. This is an implementation awaiting real Mint game acceptance; it does not prove reliable movement around steps, doors or true server noPath resolution. See `docs/HANDOFF_2026-10-19_MOVEMENT.md`.

## Boundaries

1. **Mindcraft integration (Mint-local)**: original runtime `agent.js`, action command list, `skills.js` and mode scheduler own protocol/chat and bridge calls. The project installer never overwrites these entry points without inspecting exact local source.
2. **Alice core**: manages state and durable player intent; resolves mode priority. States include IDLE, FOLLOW, COMBAT, GUARD, SURVIVE, GATHER, CRAFT, RECOVER, EXPLORE, STORAGE.
3. **Movement**: single pathfinder owner during FOLLOW; normal paths cannot dig/build. Recovery is bounded: repath, jump, relevant obstacle dig, safe descending, Pathfinder-based scaffolding/pillaring. Destructive moves are last-resort and remain experimental.
4. **Tasks**: explicit recipes/primitive skills; no unrestricted code generation. `collectWoodSmart` checks progress and excludes failed block positions; `learnBasicWeapon` composes logs/planks/table/sticks/sword.
5. **Learning**: records real position/inventory outcomes; scores allowlisted strategies in `bots/<agent>/alice_learning.json`. It **does not** train model weights or write/execute arbitrary JS.
6. **Autonomy**: 20-second idle grace, 2-minute job cooldown, runs only with IDLE and no active action or FOLLOW intent. Deterministic basic self-equipment and wood reservation only.
7. **LLM**: complex plans/dialogue via existing `gpt-oss:20b` Ollama backend. Latency-sensitive follow/wood/basic weapon commands are handled by previous fast routers, which must be checked in Mint.

## Long-lived intent invariants

- Player follow is retained as intent; brief GATHER/CRAFT actions are temporary states, not implicit cancellation of FOLLOW.
- SURVIVE > GUARD/COMBAT > FOLLOW/RECOVER > GATHER/CRAFT > IDLE.
- Recovery always observes actual movement/progress; do not treat returning true from a pathfinder call as success.
- User command cancellation and respawn restore are in integration entry files and are **not** guaranteed merely by installing runtime modules.
- Automatic block break/place must be safe around player buildings, lava, falling blocks and unknown terrain. Present allowlists are conservative but do not fully establish world-claim protection. Do not call the destructive recovery implementation production-safe until tested in an isolated copy of the world.

## Future integration work

Move the Mint-local router, death/respawn listener and action manager hooks into **versioned, independently tested adapters** here after obtaining actual local source/diff. Never synthesize local content from old chat snippets or publish a replacement `agent.js` without testing compatibility.

## Safety priority, equipment and learning boundary

The reactive safety owner (`safety.js`) starts with the autonomy lifecycle, **independently of IDLE**. It records entity/health events and polls world threats every 300 ms; `safety_policy.js` decides `SURVIVE > SELF_DEFENSE > GUARD > PLAYER_TASK > AUTONOMY`. While safety is active, the Alice Core gate disables the original `self_defense`/`cowardice` modes to prevent two simultaneous PvP owners, but leaves `self_preservation` enabled. A safety-controller error is logged and the legacy mode gate is restored; this is a visible degraded state, not a hidden fallback.

Detection is deterministic: recent personal damage or immediately adjacent hostile mob triggers self-defense; critical HP triggers escape; a hostile next to the known owner or owner recently hurt triggers GUARD. Safety invokes one bounded ActionManager action that interrupts long gathering. Tool selection is Minecraft knowledge (prefer an axe for logs via the tool plugin; choose a sword for combat). Recipe discovery consults Mindcraft/Minecraft registered recipes, then evaluates actual inventory outcomes and saves skill experience. These are *facts plus learned execution experience*, not unsupervised model training or emergent recipes.

Interrupted `collectWoodSmart` stores remaining count and message epoch so safety can resume it when danger clears **unless a newer user message superseded it**. This mechanism has not been tested against live Mint action-manager/mode timing; it must be verified against the actual installed bridge. It does not automatically resume every upstream `!collectBlocks` command, only Alice's smart gather path. User commands are not yet centrally queued while an intervention runs: a second instruction can still momentarily interrupt combat, so the hard priority is not proven end-to-end.

## Terrain and distant player tracking (phase 0.3)

`terrain_policy.js` examines block snapshots under the bot, ahead and to both sides; a one-block-wide solid lane is classified **NARROW but walkable**, an empty landing block is **DROP_OR_VOID**, lava/fire are **HAZARD**, and unloaded blocks are **UNKNOWN**. `terrain.js` adapts the classifier to actual local `bot.blockAt` reads. Following disables sprint and parkour and limits ordinary drops to one block; direct jump recovery is forbidden without confirmed landing support. Alice observes/logs terrain status changes while tracking a visible player. This is a conservative local safety check, **not** 3D world understanding or proof against every edge collision.

`tracking.js` prefers live `bot.players[name].entity.position` and records last visible position for at most 30 seconds. When the player becomes invisible, Alice navigates to this recent waypoint and tries to reacquire the actual entity. If data is unknown/stale, Alice waits safely rather than guessing location or teleporting. The optional Paper plugin `server-bridge/` can publish allowlisted online-player positions (no OP and no remote network endpoint) into the local `bots/<bot-name>/player_locations.json`. Locations must have matching dimensions, numeric coordinates and fresh millisecond timestamps. Even with location feed, Alice still needs to navigate ordinary terrain and cannot teleport or cross dimensions automatically. The feed is intentionally **disabled by default** and is not deployed by the one-command Alice update script.

## Health-aware combat tactics (phase 0.3)

`safety_policy.js` chooses combat tactics deterministically:
- HP <= 8/20: **RETREAT** along cautious Pathfinder route, no blind lateral stepping over a cliff.
- HP 9–13: **KITE_RECOVER** (evade and avoid melee while vulnerable).
- HP >= 14 with a recent hit: **EVADE_COUNTER** (bounded retreat then counterattack if still healthy).
- HP >= 14 otherwise: **ATTACK** using a suitable equipped weapon.
- A nearby creeper is an exception: retreat rather than rushing into melee.
- If hungry after gaining separation, Alice can eat known food. Eating supports natural regeneration; it does not instantly restore HP.

Reactive survival outranks guarding the player and all work tasks. These are fixed safety rules; only bounded choice/outcome strategies should be learned. There is no guarantee of winning combat, avoiding ranged projectiles or finding a safe retreat in every terrain. The effect of competing upstream Mindcraft modes and new commands remains a real Mint acceptance test.

## Social / activity architecture (phase 0.4)

- `social_policy.js` is a pure lexical classifier for a small set of read-only status questions and obvious non-command smalltalk. **Unrecognized or command-like text always falls back to Mindcraft's existing message router**, with no new authorization restrictions.
- `activity.js` observes AliceCore action start/end lifecycle and listens for recent *matching* chat/whisper instructions. It does **not** treat the last person who happened to chat as the task owner. Unmatched/system commands are reported as unverified or autonomous, avoiding false attribution. Provenance is best-effort when Mindcraft's local fast router has not yet been migrated into the versioned adapter.
- `social.js` decorates the existing `agent.handleMessage` instance method at runtime when AliceAutonomy starts. Status queries return immediately without LLM or actions. Optional chat-only Ollama HTTP calls are bounded by timeout, concurrency and output sanitization, and are **not** passed to the command executor. Model failure never changes Alice's current task. No `agent.js`, `ActionManager`, pathfinder, server or Mineflayer movement code is changed by this module.
- Autonomous quips use locally curated Minecraft comments (no model inference) with an idle-only condition, 8-minute quiet window, nearby human, no combat threat and probability throttling. Autonomous chat is not a separate recurring task in ActionManager.
- `autonomy.js` creates/starts/stops `AliceSocial` alongside but **independent from** `AliceSafety`. The safety controller remains higher priority than all social behavior.
- Player privacy: only short recent social chat exchanges reside in process memory (not committed). No messages go to a new model unless a chat URL/model is explicitly configured; the default conversation path remains existing Mindcraft settings.
